## Ownership and messages

One worker exclusively owns `BTreeMap<map_id, Option<NavigationMap>>`, including lazy directory discovery, tile reads, decoding, Detour insertion and query scratch. `NavigationMap` already implements `Send`; neither maps nor their mutex remain accessible to simulation callers. Main-thread `Navigation` owns entity route progress, current request IDs, pending continuations and completed results. No worker touches ECS, movement, ground/LOS resources, logging decisions or replication.

`Request { entity, id, map_id, query }`: monotonically increasing request ID; `query` is ordinary path, smooth waypoint path, surface collision ray, or a batch of candidate paths. Each variant captures input coordinates; a candidate batch is one entity request, not eight requests that supersede each other. `Response { entity, id, result }` carries owned points/collision/candidate results, retaining `Result<Option<_>, String>`: success, genuinely unbaked map, or the unchanged query error. Pending is separate from all three. The surface-ray variant includes today's map-initialization query; no synchronous shortcut remains.

Submission never blocks. The queue coalesces to at most one live queued request and one retained completion per entity, plus the worker's single executing job; obsolete in-flight work is not another live intent. There is no unbounded notification/job channel. Repeated polling of an unchanged pending intent does not allocate another ID. New entity intent supersedes the older ID; cancellation, map/goal changes and existing route-invalidating conditions invalidate the ID. The worker coalesces queued obsolete requests; responses for noncurrent IDs or retired entities are dropped. Existing replan thresholds, route geometry and error text remain unchanged.

## Publication and pending movement

At the start of each fixed tick, before any movement consumer, nonblocking collection snapshots a completion set and sorts it by `(entity bits, request ID)` before applying current results. Identical completion sets produce identical application order. Worker arrival timing may change which tick receives a result; determinism is not claimed across different completion sets. Existing routes and actor state remain on the simulation thread.

While pending, continue the current route when present; otherwise hold position. Follower hazard escape specifically holds during its user-approved reaction window and while its escape plan is Pending; [project reaction policy](../../specs/navigation.md#follower_hazard_reaction_policy) supersedes immediate escape timing. Do not classify pending as blocked/unbaked, start a no-path timeout, invent a destination, emit arrival, or substitute direct movement. Ready paths enter the existing corner/spline followers; preserve route ownership and real-position validity. Query errors take the same caller error/log/hold branch as today, only after completion. Genuine unbaked results remain distinct from pending; do not expand or silently alter the existing contract's unbaked-map behavior.

Raw probes and movement share one latest worker slot per entity. A pending raw probe retains the published route but prevents route resubmission from replacing that probe; ordinary movement may continue the published route without claiming arrival for the probe. A completed probe is reused within existing position/replan tolerances so every tick does not restart it before a route can finish. New raw intent invalidates an older pending route, not its published progress. Cancellation/pruning also clears raw IDs, including player fear and non-creature script movers. Ready results, including worker failures, use the same sorted publication path.

Fear captures one random destination, awaits collision, performs existing main-thread LOS clipping, then requests its path. Hazard selection captures one candidate batch until completion, then revalidates its endpoints/routes against current fields before applying the existing shortest-route choice. Native aura395 grows each tick; regenerating query identity from that radius starves publication. Source radius curves and RNG are unchanged; follower escape now follows the explicit [50ms prediction/250ms reaction project policy](../../specs/navigation.md#follower_hazard_reaction_policy), not Retail timing. Selected owned candidate corridors install directly without a second worker query. A pending probe is not a false/clear decision. Waypoints retain their current spline/hold and do not advance node/start/arrival state merely because work was queued. Production never drains or joins the worker during a tick. Tests alone get `drain_until_idle`, followed by normal ordered publication.

## Worker failure

Catch and log a worker panic; detect worker exit/disconnection as well. Fail every outstanding/current request with an explicit worker-unavailable error, and reject future requests with that error rather than leaving Pending forever. Do not restart silently or add synchronous fallback. A worker-death control checks all pending and subsequent requests terminate explicitly.

## Worker-migration proof and exclusions

First RED: real baked tile read held at its actual IO boundary while an App advances fixed ticks. Assert ticks advance and no path publishes while held; release, drain only in the test, run the next fixed tick, and assert the real path publishes and movement resumes. Add behavioral controls for existing-route continuation, latest-request wins, stale completion rejection, stable publication order, unchanged errors, fear/hazard/waypoint continuations and drain isolation.

## Encoded navigation grid contract

Verified geometry failure: City of Threads map2669/tile31_37/Detour(106,127) has69452 contour vertices,68202 after pinned Recast vertex deduplication, exceeding `rcBuildPolyMesh`'s16-bit `0xfffe` capacity. Removing the guard would corrupt indices. The real authored-tile regression reproduces this failure; first-pass bakes also fail the same stage on2660,2874,2859. Receipts and pre-fix hashes live in `game-engine/data/diagnostics/follower-dungeons-2026-10-21/`.

Lead-approved refinement starts each complete map at the existing4×4 grid. Only the explicit Recast contour-vertex capacity error doubles subdivisions per axis and restarts the entire map; no tile may retain a different grid. Allocation, geometry and other Recast errors remain fatal. Refinement is bounded by the existing2048 voxel cells per WoW tile, not a map-specific setting. Voxel size/height, body radius/height, climb, slope, region sizes and contour/detail simplification remain unchanged. Ordinary4×4 `.nav` payloads must remain byte-identical.

`OSSONAV3` retains its packet framing. Each existing Detour packet already encodes bounds and grid coordinates. The worker initializes its map's Detour tile width from the first validated nonempty packet, normalizes only floating-point coordinate-rounding error to the encoded power-of-two grid, and rejects any subsequently loaded packet with a different grid. Packet-count validation is bounded by actual artifact length, not the former16-packet assumption. Empty tiles do not select a grid or permit a direct route. A wholly empty loaded map fails explicitly before a Detour query. No simulation-thread IO/query path is introduced.
