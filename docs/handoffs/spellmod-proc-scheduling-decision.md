## 3. Recommendation and blast radius

**Recommend (a): one synchronous, source-qualified proc-dispatch path at TC's phase points.** It is the only listed option matching the pinned ordering without parallel consumption semantics. This is a broader event-scheduling change, not a five-line consume-point relocation.

Current engine `auras/procs.rs:159–163` only queues;222–235 drains later, and520–522 spends. `auras/mod.rs:160–178` schedules that drain in FixedUpdate after casts, queued triggers and auto-attacks. Deleting the direct drain alone cannot satisfy the same-call contracts.

Blast radius includes actor/recipient proc ordering, periodic/melee/spell producers, proc scripts and triggered children, same-tick re-procs/cooldown changes, aura interrupts, and the after-event Dance/Mystic Touch hooks currently executed by the drain. Existing class AfterCast consumers must not double-consume or lose their follow-up effects when a proc now removes an aura earlier. Holy's existing comment explicitly spends Surge before queued heal events can re-proc it; synchronous HIT dispatch changes that ordering and needs source-consistent reconciliation, not changed expectations.

Re-entrancy becomes immediate: mirror pinned `Unit.cpp:5591–5596` chain limit10 and10678/10685 chain/removal checks. Record exact per-spell ownership through nested casts. Replace queue-based test observation with an explicit test observer rather than a compatibility queue that dispatches again. The shared effective-entry loader and actual event context are prerequisites (absent from this isolated branch and the last inspected canonical46c2 source); reuse the qualified implementation, not another parser or guessed phases. Full gate/numerical requalification belongs to main after targeted proof.

**(b) REQ-only inline charges, effects queued:** smaller unrelated-effect timing blast radius, but a second per-event lifecycle. It needs single eligibility/chance/cooldown preparation, explicit already-prepared ownership and stable aura lifetime, or it risks re-rolls, double consumption and stale queued aura effects. It does not cover non-REQ stack consumers and cannot reconcile the Stormkeeper missing-entry conflict. It is not equivalent to pinned inline preparation→effects→removal.

**(c) generic inline preparation with deferred effects/removal:** avoids restricting charge ownership to REQ8 but still splits a proc across times. Deferred removal fails immediate NSw absence; early removal can invalidate queued handlers and reverses TC's effects-before-final-removal order. More state, not a simpler source-faithful solution.

Direction(a) is chosen. No implementation or more fixtures until main reviews Stage1 below. Historical Fiery145261 and Revealed Flaw28815 results remain preserved but are withdrawn as TC-positive consumption oracles because neither has an eligible proc entry; no fabricated metadata will make them consume.

### D. Composition, ownership and guards

**pe1098 composition.** Keep its event-time actor/target instance boundary and native traversal order. Its HashSets restrict membership; they must not become iteration order. After both sides are captured, prepare actor, actual mod-owner, then target before executing actor then target. Prepared invocations hold owner-qualified `(Entity, instance_id)` and admitted effect masks, not a later scan by spell ID. A refresh retains identity; replacement/removal does not. One actor callback cannot admit a new target aura into the same event or change target chance before target preparation. Mod-owner forwarding follows `Unit.cpp10646–10657` only when the actual owner relationship exists; do not infer it from class or invent a caster/target.
