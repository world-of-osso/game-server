Follower formation destinations use a collision-limited, walkable point connected to the owner's polygon; shrink the requested offset toward the owner when the requested point cannot be connected. The follower then follows its production navmesh route to that point. Evaluate follower approach exposure along the complete native route, including every continuation of a partial corridor. If the complete route is unavailable, hold rather than treating the unchecked remainder as safe.

Ground correction must not move a routed follower below its navigation step by more than the walkable step height. Hold and repath instead. Only an authored navigation route or a registered Drop passage can admit a larger descent.

When the follower's regroup corridor crosses an unpulled hostile's aggro radius, it follows a safe route to a recent point on the owner's out-of-combat trail. It rechecks when that hostile is pulled. If no safe route is available for five seconds, it resumes ordinary following instead of holding indefinitely. This is the user-directed follower policy, not a claim of Retail behavior.

Followers select a hostile only when a complete navigation corridor reaches it, or when an available hostile spell can reach it with line of sight. They drop a current target that no longer meets either condition. The same eligible enemy set feeds the primary selection and the follower kit.

Class-follower roster portraits use the same race, customization and head equipment as their `CharacterVisual` and `EquipmentAppearance`; they do not carry an NPC display ID. Explicit story-NPC diagnostics retain their actual template display. Class followers use player combat reach and race/sex eye geometry, and retain player-derived maximum-mana aura bonuses; ordinary NPCs retain their native behavior. ### Private live queue fixture

With a solo level-90 damage character connected to a private server, run `game-engine-cli --socket /tmp/game-engine-<pid>.sock lfg queue --role damage --dungeon-id 2436`. The queue admits Ruby Life Pools, map 2521, difficulty 205. The party contains the player, one tank, one healer and two damage followers; the server logs the random seed and selected specs. The six core appearance selectors currently use index zero; only sex varies by seed. Keystone admission and band gear are outside this fixture. Live execution of this fixture is not yet verified.

A dead follower's corpse persists for the active dungeon run, including an owner disconnect, and remains eligible for ordinary party resurrection. This is the user's follower policy, not generic summon behavior: TC 15e0ed76 `Creature.cpp:430-438` removes a corpse and `TemporarySummon.cpp:73-80` unsummons a dead summon. TC `SpellEffects.cpp:3688-3715` calculates resurrection health and mana for dead players; followers accept the existing party spell effect in place. While any party member is in combat, it remains dead. After combat, it releases and revives at the shared dungeon release location only when the production Follow navmesh query returns a complete route to its owner. Otherwise it waits for resurrection at its corpse. There is no distance threshold or transport-aware route shortcut; normal Follow movement returns a released follower to its owner.

Dungeon spirit release uses one location policy for players and followers: a zone graveyard on the instance map, otherwise the authored dungeon entrance, otherwise the reciprocal exit. A dungeon release resurrects at that location. TC 15e0ed76 `Player.cpp:4688-4720` supplies the dungeon resurrection semantics; the location order is the user decision. After combat, a follower releases only if a complete route from the release point to the owner takes at most 120 seconds at the follower's run speed; longer routes wait for a resurrection (user decision, to make this rare). The asynchronous complete-route query chains navigation segments and reports incomplete routes rather than treating an intermediate portal as a destination. It starts at the release point, not the corpse; normal navigation pruning must not cancel it merely because the corpse is elsewhere.

For an in-memory follower run, disconnect and logout retain the same instance and party until the empty copy unloads. TC 15e0ed76 `WorldSession.cpp:633-645,671-682` saves the player and removes them from the map; `Map.cpp:3013-3027` starts the unload timer when the last player leaves, and `World.cpp:764` sets its default to 30 minutes. An expired instance lock uses the immediate minimum delay. The same followers, including corpses, and copy-scoped progress remain in the surviving copy; on reconnect the player returns to the saved position. The existing server-restart persistence gap below is separate.

## Admin harness party staging

`stage-follower-party <owner> <map> <x> <y> <z>` is admin-socket-only setup, not gameplay
transport or dungeon traversal. It requires an online, out-of-combat owner in its admitted
follower copy, exactly the owner's current genuine follower party, and no encounter in progress.
It refuses foreign members or a destination outside that copy. One queued world operation uses
the ordinary owner teleport and places those existing followers on the same destination floor;
health, stats, auras and ownership are preserved. No runtime flag or production follow/teleport
behavior changes. Azure use explicitly bypasses
`FOLLOWER_AZURE_TRANSLOCATION_BOOK_TRANSITION_UNSOURCED`; it proves no earlier-boss progression.
