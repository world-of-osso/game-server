# Passenger mounts

Contract: [engine passenger-mount spec](../../../game-engine/docs/specs/passenger-mounts.md). Server implementation: `crates/server/src/vehicle.rs`; mount activation: `auras/mount.rs`; behavioural fixtures: `vehicle_tests.rs` and `networking_tests/receiver_rate.rs`.

Authority stays on the mount-summoning player. Boarding validates living group membership, the authoritative `InMap { map_id, instance_id }` map copy, range, available enter/exit non-control seats and local model attachment data. Boarding fixtures use `auth_character::spawn_player_entity`, the login spawn path, without synthetic player `Zone` components. Map/instance transfers eject passengers; terrain area changes within a map copy do not. Passenger movement uses MovementControl and driver-relative M2 bind-pose offsets; server does not simulate animated mount bones. Vehicle and VehicleSeat catalogs must load from deployed `world.db`, with explicit startup failure naming missing tables and `scripts/import-vehicles.py`. Creature display/model metadata must use the existing `creature_display_info` and `creature_model_data` world tables, never client CSVs. M2 attachment geometry still loads from the shipped ground models. Deployment's `scripts/ground_files.py` must include the M2s of every mount vehicle with an enter/exit, non-control passenger seat, even without map spawns. Runtime and deployment share `scripts/vehicle_models.sql` for the mount/spell/vehicle/display/model join. Only passenger seats require server bind poses; skins and skeleton companions are not read. Missing required models remain explicit startup warnings and appear under `vehicle <id>` in `ground_files.py --missing`; never discard their diagnostics. Import: `python3 scripts/import-vehicles.py <local-db2-csv-directory> data/world.db` (Vehicle seat IDs; VehicleSeat flags, attachment ID and XYZ offsets). Back up the resolved database before importing. Current verification and remaining client/live acceptance are tracked in the linked contract.
